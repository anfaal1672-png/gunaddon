# マスタープロンプト v2：ARSENAL CORE 2.0「超拡張」

> このプロンプト全体を、ファイル作成とシェル実行ができるエージェントにそのまま渡してください。
> 前提は **ARSENAL CORE 1.0.2 のソース一式（`ArsenalCore/`）が手元にあること**です。ゼロから作り直すのではなく、1.0.2 を土台に拡張します。
> 「2. 前提パラメータ」の数値だけ書き換えれば、規模を上下できます。

---

## 1. 役割とゴール

あなたは Minecraft 統合版アドオンの第一人者であり、次のすべてに精通したリードエンジニア兼ゲームデザイナーです。

- Script API
- Behavior Pack / Resource Pack
- JSON UI
- Blockbench 形式のモデリング
- 手続き的なアセット生成
- ゲームバランス設計
- マルチプレイの性能設計

**ゴール：** ARSENAL CORE 1.0.2 を **2.0.0** に拡張すること。次の 3 本柱で「これ 1 つでサバイバルも PvP もミニゲームも遊べる軍事サンドボックス」にする。**途中で質問せず、最初から最後まで一気に** 設計・実装・検証し、インポート可能な `.mcaddon` として納品すること。

1. 武器の数と深さを倍にする
2. 装備と戦場のシステムを増やす
3. 遊び方（進行・経済・ゲームモード）を加える

品質の基準は 1.0 と同じ「導入した瞬間から撃ち心地・音・見た目・操作性・バランスが気持ちいい」こと。加えて、**スマホで快適に遊べること** と **既存ワールドを壊さないこと** を最優先にする。

## 3. 絶対ルール（1.0 から継続＋追加）

1. **プレースホルダー禁止。** TODO、省略、「同様に」を残さない。全ファイルを完全な形で出す。
2. **データ駆動。**
   - 次のすべての定義は `tools/data/` 以下のデータモジュールに集約する：武器・弾薬・アタッチメント・防具・敵・構造物・ゲームモード・キルストリーク・経済・進行。
   - アイテム・アタッチャブル・言語・レシピ・テクスチャ・モデル・音は生成スクリプトで作る。
   - ランタイムと生成スクリプトは同じデータを読む。
3. **実在の商標名は使わない。**
   - 銃・メーカー・兵器システム（ミサイル・戦闘機・装甲車の名前も含む）・ゲームの名前を使わない。
   - 商標チェックのリストを 150 語以上に広げ、新しい名前をすべて照合する。
   - 衝突した名前は差し替え、`DESIGN_DECISIONS.md` に記録する。
4. **公式仕様に準拠。**
   - 実行時点の Microsoft Learn と Mojang/bedrock-samples（最新タグ）を確認する。
   - `format_version`・コンポーネント・Molang・JSON スキーマを合わせる。
   - スキーマは `tools/schemas/` を最新版に更新する。
5. **既存ワールドとの互換性。** ワールドを 1.0.2 から 2.0.0 に上げても壊れないこと。
   - 次を変更しない：既存のアイテム ID、ダイナミックプロパティのキー（`a:ammo`・`a:mode`・`a:att`・`a:at`・`a:ub`・`a:init`）、ワールド設定と個人設定のキー。
   - 新しいキーの追加と、読み込み時の移行だけで対応する。
   - 移行処理はランタイムテストで検証する（1.0.2 形式のアイテムと設定を読み込ませる）。
6. **`player.json` を上書きしない。** バニラのエンティティ・アイテム・ルートテーブルの上書きは最小限にする。上書きするものは一覧にして README に書く。
7. **全入力デバイスで遊べる。** タッチだけで全機能が使えること。とくに次を守る：
   - 押しっぱなし前提の操作には必ず代替を用意する（1.0.2 の「タップ切替」方式を全連射系・照射系に広げる）。
   - 小さい画面でも読める HUD。
8. **軽量。** グローバルループは 1 本に集約する。敵 AI・設置物・乗り物は間引きと予算制で動かす。20 人マルチ＋敵 60 体でも破綻しない設計にする（15 章）。
9. **判断はあなたが下す。** 曖昧な点は品質が最も高くなる解釈を選び、`DESIGN_DECISIONS.md` に記録して進む。
10. **1.0 系の既存機能・既存テストを壊さない。** 1.0.2 の 54 項目のテストと 17 項目の検証は、2.0 でもすべて通ること。

## 4. 1.0 系で実機から判明した落とし穴（必ず守る）

1.0.0〜1.0.2 で実機のコンテンツログとプレイヤーの報告から見つかった問題です。**2.0 の全コードとデータに同じ規則を適用し、可能なものはビルド時の自動検証にする**こと。

| # | 落とし穴 | 規則 |
|---|---|---|
| 1 | `minecraft:pushable` は現行スキーマに無く、エンティティが丸ごと読み込まれなかった | コンポーネント名は公式スキーマの一覧と突き合わせる。押せる挙動は `pushable_by_entity` / `pushable_by_block` を使う |
| 2 | Molang の `??` の左辺に構造体のメンバー（`v.color.r ?? 1`）を書くとエラー | `??` は直接の変数だけに使う。スクリプトから必ず値を渡す |
| 3 | `bones: {}` の空アニメーションはエラー | 何もしないアニメーションでも骨を 1 本入れる |
| 4 | 撃っている最中に手持ちのアイテム（ダイナミックプロパティ・耐久）を書き換えると、スマホで「使用」が途切れ、指を離しても射撃が止まらなくなった | **使用中は手持ちのアイテムを書き換えない。** 状態はメモリに持ち、指を離した時・撃ち止めて一定時間後・持ち替え時にまとめて 1 回で書き込む |
| 5 | バースト開始時に押下の記録を消費せず、1 タップで弾切れまでバーストが続いた | 入力の記録は「1 押下 = 1 動作」で必ず消費する。重複イベントに強くする |
| 6 | 遠くを撃つと未ロードのチャンクに触れて警告が出続けた | レイ・実体弾・爆発・ブロック操作の前に `isChunkLoaded` とワールドの高さを確認する。境界での同種例外はログに出さない |
| 7 | 銃口が地面や壁にめり込んだ状態で発射すると実体弾がすり抜けた。レイの始点が面上だと取りこぼした | 発射位置は目から銃口へのレイで補正する。衝突はレイ判定に加えて「終点・始点がブロック内なら進入点を探す」補正を入れる |
| 8 | エンジンの爆発ダメージが入らない場合があった | エンジンの爆発のあと、次の tick に「ダメージを受けていない対象」へスクリプトの爆風ダメージを与える（二重に当てない） |
| 9 | 高倍率スコープでの回転カメラシェイクで視点が激しく震えた | ズーム中に回転シェイクを使わない。揺れの表現は拡散か、ごく弱い位置シェイクにする |
| 10 | アクションバーの文字列は現行の HUD でグローバルバインディングとして読めない | JSON UI へのデータ受け渡しはタイトル文字列の目印（`§a§r§s§n…`）方式を使う。目印だけのタイトルは枠ごと隠す |
| 11 | 実機での確認ができない | 実機でしか分からない値（一人称の位置など）は、プレイヤーがゲーム内で調整できる手段を用意する（10.4） |

## 5. アーキテクチャの拡張

### 5.1 データの分割

1.0.2 の `tools/weapons.data.js`（約 800 行）は 2.0 で数倍になる。そのため次のように分割し、`tools/data/index.js` で 1 つの `DATA` に束ねる。ランタイムには生成時に 1 ファイルへまとめたものをコピーする。

```
tools/data/
├─ index.js            # 束ねる・整合性チェック用の派生値
├─ core.js             # 名前空間・バージョン・ティア・カテゴリ・既定設定
├─ weapons/            # カテゴリごとに 1 ファイル（handgun.js, smg.js, … melee.js）
├─ ammo.js
├─ attachments.js
├─ armor.js
├─ equipment.js        # 投擲物・設置物・医療品
├─ enemies.js          # 勢力・敵・ボス・スポーン
├─ structures.js
├─ modes.js            # ゲームモード
├─ killstreaks.js
├─ economy.js          # 通貨・価格・商人の品揃え
├─ progression.js      # 武器レベル・階級・チャレンジ
└─ recipes.js
```

### 5.2 ランタイムの追加モジュール

| モジュール | 責務 |
|---|---|
| `core/migrate.js` | 1.0.2 形式のアイテム・設定・ワールドデータを 2.0 形式へ移行 |

| `core/melee.js` | 近接攻撃（軽・強・投擲・背後からの即死） |

### 6.2 射撃システムの追加

- **照射式**（火炎放射・Photon Lance）：押している間、毎 tick の短距離判定。燃料／電力を消費し、過熱する。
- **弾道の強化**：
  - 全実体弾に風の影響（ワールド単位でゆっくり変わる。狙撃スコープの HUD に風向き表示）。
  - 弾速による命中までの遅延（ヒットスキャン武器にも「弾速」を持たせ、長距離のみ遅延させる選択肢を検討）。
  - 素材別の跳弾。
- **制圧**：至近弾（自分の周囲 2 ブロック以内を通過した敵弾）を受けると、画面の端が暗くなり（JSON UI）、拡散がわずかに増える。個人設定で OFF にできる。
- **近接**：武器を持っていない手でも使える「クイック近接」（銃床打撃）。背後からの近接は即死級にする。PvP ではワールド設定で調整する。
- **スマホ向け補助**（個人設定・既定 OFF。PvP ではワールド設定で禁止できる）：
  - エイムアシスト（ADS 時に照準近くの敵へ弱く吸い付く）
  - 自動射撃（照準が敵に重なったら撃つ）

### 7.2 3D モデルへの表示（1.0 の既知の制限を解消する）

アタッチャブルは「そのスタックだけの状態」を Molang で直接読めないため、次の順で方式を決める。

1. **調査**：実行時点の公式ドキュメントとスキーマで、スタックごとに変わり、かつアタッチャブルの Molang から読める値を探す。例：残り耐久値のクエリ、エンチャント状態、染色可能アイテムの色。使えるものがあれば、それで光学・銃口・アンダーバレルの表示を切り替える（耐久を流用する場合は、耐久システムとの両立方法を設計する）。
2. **確実な方式（必ず実装）**：光学だけは見た目に反映する。
   - 光学を 3 つの見た目グループに分ける：なし（アイアン）・ドット系・倍率スコープ系。
   - グループが変わったときだけアイテムを**見た目違いの ID**（`arsenal:<id>__o1` など）に差し替える。ダイナミックプロパティ・耐久・名前・Lore はすべて引き継ぐ。
   - 見た目違いのアイテムはクリエイティブ一覧・レシピ・図鑑から隠し、元の ID と同じ武器として扱う。
   - 生成・参照整合性・引き継ぎをテストで保証する。
3. 見た目のボーンは各アタッチメントごとに生成し、2 の方式ではグループごとに表示／非表示を焼き込む。

### 7.3 迷彩（スキン）

武器レベルで解放する迷彩を 8 種（単色 3・迷彩柄 3・金・ダイヤ風）作る。

- 7.2 と同じ理由で、迷彩の適用は「見た目違い ID」方式になる。組み合わせ爆発を避けるため、次の 2 通りのどちらかを選んで記録する。
  - 迷彩は光学グループと掛け合わせない（迷彩中は光学の見た目を代表 1 種に固定する）
  - 迷彩をレジェンダリー限定にする
- アイテム数・アタッチャブル数・テクスチャ容量の見積もりを事前に出し、上限（2 章のパッケージ上限）に収める。

## 8. 装備・防具・設置物

### 8.1 防具（3D 表示）

- **系統**：軽装・標準・重装・特殊部隊の 4 系統 × 3 段階。
- **部位**：ヘルメットとボディアーマー。アタッチャブルでプレイヤーに 3D 表示する（バニラの防具スロットを使う）。
- **性能**：部位ごとの防御（ヘルメットはヘッドショット倍率を下げる）、移動速度、耐弾性。
- **プレート**：ボディアーマーに「プレート」を差す。
  - 使用して 1 枚ずつ装着する。
  - 弾を吸収して割れる。
  - HUD にプレートの残りを表示する。
- **特殊**：
  - 暗視ゴーグル付きヘルメット（使用で ON/OFF。暗視＋緑の画面）
  - ガスマスク（ガスグレネード無効）
  - ギリースーツ（スニーク静止中に敵 AI の発見距離を大幅に下げる）

### 8.2 投擲物・医療品・設置物（8 → 24 以上）

- **投擲物**：
  - 既存 8 種はそのまま。
  - 追加：ガスグレネード、EMP（電子機器・エネルギー兵器・ドローンを停止）、クラスター、デコイ（偽の銃声で敵 AI を誘導）、投げナイフ、スナップ（センサー）グレネード。
- **医療品**：包帯（出血を止める）、メディキット（持続回復）、アドレナリン（一時的な速度と被ダメ軽減）、除細動器（ダウンした味方の蘇生）。
  - 「ダウン状態（死ぬ前に一定時間這って味方を待つ）」は PvP とゲームモード用の任意ルールにし、ワールド設定で ON/OFF。
- **設置物**：
  - センチネル砲台（自動で敵を撃つ。弾は設置者の在庫から補充）
  - 設置式シールド（弾を止める。耐久あり）
  - クレイモア（扇状の感知と爆発）
  - 弾薬ステーション・医療ステーション（範囲内の味方に補給）
  - 迫撃砲（座標指定の間接射撃）
  - 偵察ドローン（ドローン視点で操作。カメラ API が使えない場合は俯瞰の空中カメラ）
- ライオットシールドは**オフハンド装備**にする。正面からの弾を防ぎ、構え中は移動が遅くなる。

## 9. 戦場（敵・構造物・乗り物・キルストリーク）

### 9.1 勢力と敵（5 → 14 以上＋ボス 2）

| 勢力 | 構成 | 出現 |
|---|---|---|
| レイダーズ（既存を拡張） | ガンナー・ライフルマン・スナイパー・ヘヴィ・キャプテン（既存 5）＋メディック・爆破兵・犬（新 3） | 夜の平原・砂漠・荒野・サバンナ、レイダーの野営地 |
| アイアン・レギオン（新・機械） | 偵察ドローン・歩兵ロボット・シールド兵・迫撃砲ロボ（4） | 研究所・山岳 |
| ホロウ（新・変異体） | 走る変異体・自爆型・装甲型（3） | 夜の地下・廃墟、ホードモード |
| ボス | ウォーロード（レイダーズ。3 段階の行動・増援・空爆）、ジャガーノート・マーク II（レギオン。装甲の部位破壊・ミサイル・EMP） | 構造物の最奥、または召喚アイテム |

- **戦術 AI**：
  - 分隊単位で動く（隊長が目標を決め、隊員は遮蔽物を探し、側面へ回り、手榴弾を投げ、制圧射撃をする）。
  - 思考は予算制で、1 tick あたり処理する AI の数に上限を置き、各 AI は 5〜10 tick ごとに考える。
  - 射撃はプレイヤーと同じ弾道（`traceHitscan`）を使い、難易度に応じて精度を変える。
- **ボス**：ボスバー、行動の予兆（声・光・パーティクル）、部位破壊、撃破報酬（レジェンダリー確定枠）。

### 9.2 構造物（6 種以上・自然生成）

- **種類**：レイダーの野営地・前哨基地・武器庫バンカー・レギオン研究所・墜落した輸送機・廃港。
- **作り方**：
  - `.mcstructure` は Python で NBT（リトルエンディアン）として生成する。
  - `feature_rules` と `structure_template` 系の地物で自然生成する。
  - 実行時点で安定版の方式を確認し、実験的機能に頼らない。
- 守備隊の配置と宝箱の中身は、初回にプレイヤーが近づいたときにスクリプトで起動する（ルートテーブルはティア別）。
- 構造物の密度・種類ごとの出現は、ワールド設定で OFF／少なめ／標準／多めを選べる。

### 9.3 乗り物と銃座

- **銃座 3 種**：重機関銃座・対空機関砲・対装甲ランチャー座。乗ると視点で照準し、使用で射撃。
- **乗り物 1 種**：軽装甲バギー。運転席＋銃手席（銃座を搭載）、耐久、燃料、修理キット。
  - 操作は `minecraft:input_ground_controlled` と `minecraft:rideable` を使う。
  - タッチ操作で運転できることを確認する。
  - 実現性に問題があれば、銃座の完成度を優先して乗り物を次版に回し、理由を記録する。

### 9.4 キルストリーク（6 種）

連続キル（死ぬとリセット）で解放し、「ストリーク端末」アイテムから選んで使う。

- 偵察（範囲内の敵を発光）
- 補給投下（落下する箱からランダム報酬）
- 砲台投下
- 空爆（直線上の連続爆発）
- EMP
- ガンシップ（上空から照準して撃つ。視点の扱いはドローンと同じ）

PvE ではキル数の代わりにポイントで解放する。ワールド設定で無効化できる。

## 10. 遊び方の拡張

### 10.1 進行

- **武器経験値と武器レベル**：
  - 武器ごとに 1〜30。キル・ヘッドショット・アシストで経験値が入る。
  - レベルでアタッチメントの作成レシピと迷彩を解放する。
- **階級**：プレイヤーごとに 1〜50。称号と、名前の横に付く階級グリフ。
- **チャレンジ**：デイリー 3 件・ウィークリー 3 件。報酬は通貨と経験値。
- **統計**：キル・デス・命中率・ヘッドショット率・最長キル距離・武器ごとの使用回数。
- 保存先はプレイヤーのダイナミックプロパティ。文字列長の上限を踏まえて、分割保存とバージョン付きの形式にする。

### 10.2 経済

- **通貨**「クレジット」（アイテムではなく数値。HUD と図鑑に表示）。
- **商人**：「補給係」NPC（村の近くや構造物に出現）がフォームで武器・弾薬・パーツを売買する。
- **闇市**：日替わりのレジェンダリーやレアパーツ。
- 価格はデータ駆動にする。売値と買値の差でインフレを防ぐ。
- ワールド設定で「経済なし（作業台のみ）」にもできる。

### 10.3 ゲームモード（4 以上）

- **共通基盤**：
  - OP が「アリーナツール」でアリーナの範囲・チームのスポーン・旗の位置を登録する。
  - ロビーで参加受付し、装備セットを配布する。
  - ラウンド、スコアボード、終了時の結果画面を用意する。
  - 終了後はプレイヤーのインベントリと位置を元に戻す（開始時に保存）。
- **モード**：
  1. **フリー・フォー・オール**
  2. **チームデスマッチ**
  3. **ガンゲーム**：キルごとに武器が変わり、最後は近接。
  4. **ホード**：協力。ホロウ勢力のウェーブ、ウェーブ間の買い物、ボスウェーブ。
  5. （余力があれば）陣取り
- 途中退出・再参加・サーバー再起動でアリーナが壊れないこと（状態はワールドのダイナミックプロパティに保存し、起動時に復旧する）。

### 10.4 実機でしか分からない値の調整手段

- **一人称の位置調整**：
  - 個人設定に「一人称の銃の位置（上下・前後 各 5 段階）」を追加する。
  - 位置違いの ADS／構えアニメーションを生成しておき、設定で切り替える。
  - `/scriptevent arsenal:calib` で調整モード（その場で段階を送りながら確認）に入れること。
- **HUD の位置と大きさ**：HUD 2.0 の各要素の位置と大きさを個人設定で調整できる。
- **不具合報告**：`/scriptevent arsenal:report` で、次を 1 画面にまとめて表示する。
  - バージョン、主要設定、直近のエラー（`logError` の記録）、プレイヤーの状態
  - スクリーンショットで報告できるようにする。

## 11. UI・HUD 2.0

- **HUD 2.0（JSON UI）**：1.0.2 のスコープ表示と同じ「タイトル文字列の目印」方式で拡張する。
  - 目印の後ろに固定長のフィールドを符号化し、JSON UI の文字列演算（`-` と `'%.Ns' *` による切り出し）で読み取る。
  - 表示するもの：中央のヒットマーカー、被弾方向の表示、動的なクロスヘア（拡散に連動）、弾数ウィジェット、キルフィード、プレートと体力、方位バー、ゲームモードのスコア、制圧の画面効果。
- **フォールバック**：個人設定「HUD：クラシック（1.0 のアクションバー）／HUD 2.0」。既定は HUD 2.0 にし、JSON UI が崩れた場合にすぐ戻せるようにする。
- **バニラ UI の扱い**：置き換えはしない。追加は `root_panel` への挿入と、目印のタイトル枠を隠す処理だけにする。変更箇所は `DESIGN_DECISIONS.md` に全部列挙する。
- **フォーム UI**：
  - 作業台・商人・図鑑・設定・アリーナ管理を、カテゴリ → 一覧 → 詳細の 3 段で統一する。
  - 図鑑では、武器ごとのステータスグラフを文字グリフの棒グラフで出し、レベル・迷彩・統計も見られるようにする。
- **ガイド**：野戦マニュアルを章立てにする（射撃・装備・経済・モード・スマホ操作）。初回だけ、状況に応じたヒントを出す。

## 12. アセット

- **3D モデル**：
  - 新武器 45 種は既存のパーツビルダー（`modelgen.py`）を拡張して作る。
  - 追加するパーツ：近接武器・火炎放射器・重機関銃・迫撃砲など。
  - 防具・設置物・乗り物・新しい敵・ボスのジオメトリも手続き生成する。
  - 生成物は Blockbench で開けること（`format_version 1.16.0` 以降）。
- **テクスチャ**：
  - 64×64 の素材アトラス方式を継続する。
  - 迷彩柄は手続き生成する（ノイズ・ディジタル迷彩・タイガーストライプ等を関数で）。
  - アイコンは 32×32 の側面図レンダリングを継続し、見た目違い ID のアイコンも自動で作る。
- **音**：
  - `audiogen.py` を拡張して、次を合成する：新しい銃声プロファイル（重機関銃・火炎放射・エネルギー照射・近接の風切りと打撃）、防具の被弾音、乗り物のエンジン、ボスの声、UI 音。
  - 屋内／屋外で残響を変える（頭上のブロックを調べて、屋内なら短い残響の別サンプルを鳴らす）。
  - 音声ファイルは 450 以下に抑える。
- **パーティクル**：すべて公式スキーマで検証する。マテリアルはバニラにあるもの（`particles_alpha` / `particles_blend` / `particles_opaque`）だけを使う。

## 13. 互換性と移行

- `core/migrate.js` で、読み込み時と装備時に次を行う。
  - 1.0.2 のアイテム・設定・ワールドデータを検出する
  - 新しいキーに既定値を入れる
  - 形式のバージョン番号（`a:v`）を付ける
- 見た目違い ID（7.2）は、元の ID と相互に変換できること。アドオンを外して入れ直しても、ワールドにある武器が失われないこと（見た目違い ID のアイテムは、元の ID に戻す手段を用意する）。
- バニラのルートテーブルの上書きは 1.0.2 の 9 種から増やさない。新しい構造物は独自のルートテーブルを使う。
